En un coup d'œil

  • Un jeu = un plug-in. Chaque jeu implémente IGameModule et s'enregistre dans un GameRegistry — l'accueil, la navigation et le kernel n'ont jamais besoin d'être modifiés pour accueillir un nouveau jeu.
  • Une seule porte de sortie. Le reste de SHALOM (portefeuille, SaaS, communauté) n'importe jamais l'intérieur du module : uniquement features/bible-games/index.ts, son API publique.
  • Le score ne se calcule jamais sur l'appareil. Les gains d'XP et la validation des réponses passent par des fonctions Postgres security definer — impossible de tricher en modifiant le client.
  • Domaine pur, dépendances aux bords. Les entités et règles métier ne connaissent ni React Native, ni Supabase — seules les couches data/presentation en dépendent, ce qui rend le domaine testable et portable.
01

Vision globale du module

Jeux Bibliques est une fonctionnalité de gamification biblique — quiz, devinettes, associations, défis quotidiens — assise sur un système commun de progression (XP, niveaux, badges, classement). Son exigence structurante n'est pas fonctionnelle mais organisationnelle : elle doit pouvoir grandir, être testée, débranchée ou remplacée sans jamais toucher au reste de l'application.

Trois idées gouvernent toutes les décisions qui suivent :

  1. Indépendance totale. Le module ne dépend que d'un socle partagé très restreint (client Supabase, design system, auth, i18n). Il n'importe jamais de code des features portefeuille/SaaS/communauté, et n'est jamais importé par elles au-delà de son point d'entrée public.
  2. Extensibilité par ajout, jamais par modification. Le catalogue de jeux prévu (Quiz, Qui suis-je, Verset Caché, Mots Mêlés, Associer, futur Mode Aventure) n'est pas une liste figée mais une preuve que l'architecture doit accueillir un jeu n+1 sans toucher au code des jeux 1…n. C'est le critère de réussite de ce document.
  3. La progression est transverse, pas dupliquée. XP, niveaux, badges, streak, classement et statistiques ne sont pas la propriété d'un jeu : ce sont des concepts du kernel du module, consommés par tous les jeux via les mêmes ports.

Concrètement : livrer un sixième jeu doit être un travail d'implémentation dans un nouveau dossier games/<nouveau-jeu>/ plus une ligne d'enregistrement dans le registry — jamais un chantier de refactorisation transverse.

02

Architecture proposée

Une combinaison de trois styles qui se complètent à des échelles différentes : Feature-First au niveau de l'application, Clean Architecture au niveau du module, et un pattern Plugin au niveau de chaque jeu.

Les quatre couches, par module

Chaque brique du module (le kernel, comme chaque jeu individuel) est traversée par les mêmes quatre couches, avec une règle de dépendance à sens unique : la presentation dépend du domain, la data implémente le domain, jamais l'inverse.

CoucheContenuDépend de
DomainEntités, value objects, énumérations, ports (interfaces repository/service), use-casesrien (TypeScript pur)
DataImplémentations des repositories, datasources Supabase, mappers DTO ↔ entité, cacheDomain
PresentationÉcrans, composants, hooks React Query, view-models, stores Zustand locauxDomain (jamais Data directement)
InfrastructureServices transverses : audio, animation, notifications, analyticsDomain (via ports)

Le pattern Plugin de jeu

Chaque jeu implémente une interface commune IGameModule (métadonnées, écran d'entrée, moteur de scoring, use-cases) et s'enregistre dans un GameRegistry lu par l'écran d'accueil et le router. Ajouter un jeu = ajouter une implémentation ; retirer un jeu = retirer une ligne d'enregistrement. C'est l'application directe du principe Ouvert/Fermé (SOLID) au niveau produit.

04

Responsabilités de chaque dossier

DossierResponsabilité
app/bible-games/Déclare les routes Expo Router et le layout de navigation. Ne contient aucune règle métier : chaque écran importe un composant de page depuis features/bible-games/.../presentation.
core/domain/Vérité métier partagée : ce qu'est un joueur, un badge, un niveau — indépendant de toute technologie. Testable sans mock.
core/data/Traduit les entités du domaine vers/depuis Supabase. Seul endroit du kernel qui « sait » que la persistance est Supabase.
core/presentation/Hooks et stores exposant l'état joueur/XP/badges à n'importe quel jeu, sans qu'un jeu ait besoin de connaître Supabase.
core/game-registry/Le point d'articulation de toute l'extensibilité : contrat IGameModule, table d'enregistrement, résolution dynamique par id.
games/<jeu>/Un jeu = un sous-module Clean Architecture complet, autonome, qui ne référence jamais un autre dossier de games/.
gamification/Sous-domaines transverses (XP, badges, niveaux, récompenses, streak) suffisamment volumineux pour mériter leur propre dossier plutôt que de tout entasser dans core.
social/leaderboard/Classements et — plus tard — défis entre amis, ligues.
shared/Composants et utilitaires réutilisés par ≥2 jeux uniquement. Seuil volontairement strict pour éviter l'abstraction prématurée (KISS).

11

Proposition de schéma Supabase

Toutes les tables du module sont préfixées bg_ (Bible Games) : l'isolation architecturale du module se prolonge jusque dans le schéma de base de données. Aucune migration SQL n'est écrite ici — uniquement la conception.

Principe anti-triche : les colonnes de progression (xp_total, current_level, score) ne sont jamais écrites directement par le client. Toute mutation passe par des fonctions Postgres security definer (ex. submit_game_session(...)) qui valident les réponses côté serveur, calculent le score et insèrent atomiquement la session + la transaction XP.

Flux de données

Exemple de bout en bout : un joueur termine un Quiz. Le même flux s'applique à tous les jeux, seul le ScoringService injecté change.

sequenceDiagram
  participant UI as Écran Résultat (presentation)
  participant Hook as useSubmitQuiz (React Query mutation)
  participant Svc as GameSessionService
  participant Score as ScoringService (Quiz)
  participant Repo as GameSessionRepository
  participant DB as Supabase RPC submit_game_session
  participant XP as XPService
  participant Badge as BadgeService
  participant Store as usePlayerStore / useBadgesStore

  UI->>Hook: soumettre réponses
  Hook->>Svc: submitSession(sessionId, answers)
  Svc->>Score: computeScore(answers)
  Score-->>Svc: score
  Svc->>Repo: persistSession(session, score)
  Repo->>DB: rpc submit_game_session(...)
  DB-->>Repo: session validée + xp_awarded
  Repo-->>Svc: GameSession (entité domaine)
  Svc->>XP: awardXP(player, xp_awarded)
  XP-->>Svc: nouveau total + level-up ?
  Svc->>Badge: evaluate(player, session)
  Badge-->>Svc: badges débloqués (0..n)
  Svc-->>Hook: résultat complet
  Hook->>Store: mise à jour optimiste (XP, niveau, badges en file)
  Hook-->>UI: invalider caches React Query (historique, stats, classement)
  UI->>UI: RewardAnimation si level-up / badge

Le score n'est jamais fait confiance côté client : la RPC recalcule et valide avant d'écrire.

  • État serveur (questions, session persistée, classement, stats) transite par React Query, avec des clés namespacées ['bible-games', …].
  • État client éphémère (réponses en cours de saisie, chronomètre) reste dans useGameSessionStore et ne touche jamais le réseau avant la soumission finale.
  • Effets de bord de gamification (XP, niveau, badges) sont toujours déclenchés en réaction à une session persistée côté serveur — jamais de manière spéculative avant confirmation.

Recommandations techniques

  • TypeScript strict partout, avec un alias de chemin dédié @bible-games/* pointant sur src/features/bible-games.
  • Linter de frontières (ex. eslint-plugin-boundaries) interdisant tout import de features/bible-games/** depuis l'extérieur du module, sauf via features/bible-games/index.ts ; et interdisant les imports croisés entre dossiers de games/.
  • API publique explicite : index.ts n'exporte que ce qui doit être consommé ailleurs (composant de navigation racine, fonction d'initialisation du registry). Tout le reste est un détail d'implémentation.
  • Feature flags pilotés par la colonne bg_games.is_active (et un flag remote équivalent côté app) pour activer le Mode Aventure progressivement, sans redéploiement à risque.
  • React Query : staleTime long pour les référentiels (questions, badges, niveaux) qui changent rarement, court pour le classement.
  • Validation Zod colocalisée avec chaque entité, appliquée à la frontière des repositories pour parser défensivement les réponses Supabase.
  • Gestion d'erreur explicite via un type Result<T, E> partagé dans les use-cases, plutôt que des exceptions qui traversent les couches silencieusement.
  • Injection de dépendances légère (factory/context simple, pas de framework DI) pour brancher les implémentations de repository dans les services et faciliter les doublures de test.
  • Contenu i18n-ready dès le départ (colonne locale sur les tables de contenu) : le contenu biblique devra être multilingue tôt ou tard.
  • Lazy loading par jeu (React.lazy / import dynamique de l'écran) pour que le catalogue de jeux grandisse sans alourdir le temps de démarrage.
  • Pagination systématique sur historique et classement ; mémoïsation des listes lourdes.
  • Tests en pyramide : domaine (use-cases, stratégies de scoring) en TypeScript pur sans mock ; repositories testés contre un projet Supabase de test ; composants critiques (ResultModal, XPBar) en tests de composant.
14

Bonnes pratiques

  • SOLID appliqué concrètement — SRP : un service = une responsabilité. OCP : un nouveau jeu s'ajoute via le registry, jamais en modifiant le code existant. LSP : tout IGameModule est interchangeable par l'accueil et le router. ISP : des ports fins (IQuestionRepository, IVerseRepository) plutôt qu'une interface générique fourre-tout. DIP : les services dépendent d'interfaces, jamais d'un client Supabase concret.
  • DRY sans abstraction prématurée (KISS) — un concept ne rejoint le kernel partagé que lorsqu'il sert réellement ≥2 jeux (XP, session, scoring). En dessous de ce seuil, dupliquer dans le jeu concerné est préférable à une abstraction fragile devinée trop tôt.
  • Convention de nommage cohérente — dossiers en kebab-case, composants en PascalCase, use-cases nommés par un verbe d'action (submitQuizAnswer.ts, calculateStreak.ts).
  • Checklist de revue de code dédiée — toute nouvelle fonctionnalité de jeu doit : passer par le GameRegistry, ne rien importer d'un autre dossier de games/, et ne rien exposer en dehors de son propre dossier sauf via le kernel.
  • Documentation vivante par jeu — un court README dans chaque games/<jeu>/ décrivant les règles et la formule de scoring, utile puisque ce document ne détaille volontairement pas la logique métier.

Évolutions futures

Chaque besoin d'évolution listé par le produit trouve une extension naturelle dans cette architecture, sans refonte structurelle.

ÉvolutionComment l'architecture l'absorbe
Jeux multijoueursLes ports sont déjà découplés de Supabase ; une nouvelle implémentation RealtimeGameSessionRepository branche les canaux Supabase Realtime sans toucher aux use-cases.
Défis entre amisNouvelle sous-feature social/challenges-friends réutilisant ChallengeService et PlayerRepository ; ajout d'une table bg_friend_challenges.
Ligues, saisonsExtension du modèle de classement avec un season_id et une table bg_seasons — bg_leaderboard_entries n'est pas restructurée.
Événements spéciaux, récompenses temporairesL'entité Reward possède déjà is_temporary/expires_at — aucune extension du modèle nécessaire.
